# server.* / redis.* Lua API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run unchanged Redis/Valkey EVAL scripts in `lua.wasm`: the full `server.*`/`redis.*` table, `KEYS`/`ARGV`,
Valkey's global patches, and a Java `Handler` that receives every server-touching operation under a fixed reply contract.

**Architecture:** All Lua-facing behaviour (argument checks, error formatting, reply → Lua conversion) is ported C in
`lua/valkey_lua.c`, compiled with Valkey's own `sha1.c`, `rand.c` and `fpconv_dtoa.c`. Every delegated operation
crosses one Wasm import, `env.host_call(op, req, req_len, reply_out, reply_len_out)`, carrying a RESP2 array of bulk
strings in and a RESP2 reply out. `ValkeyLua` dispatches `op` to a `Handler` method and turns exceptions into `-ERR`.

**Tech Stack:** C (wasi-sdk 34, Lua 5.1 from Valkey `deps/lua`), Java 17, Chicory 1.7.5, JUnit 6.

**Spec:** `docs/superpowers/specs/2026-10-21-redis-api-design.md`. Read it first; this plan argues from it.
Valkey reference source (pinned `VALKEY_SHA` in `lua/Makefile`): `src/modules/lua/script_lua.c`, `engine_lua.c`.
Fetch it with `curl -sSfL https://github.com/valkey-io/valkey/archive/<VALKEY_SHA>.tar.gz | tar xz` into a scratch dir.

## Global Constraints

- RESP2 only between module and host.
- Every reply buffer the host returns is allocated with the module's exported `alloc`; the C side frees it.
- Ported Valkey C keeps Valkey's function names, comments and error strings verbatim (e.g. `luaPushErrorBuff`,
  `luaRedisPcall`, `"server.setresp() requires one argument."`), so it diffs against upstream.
- New Valkey sources come from the same pinned tarball via `lua/Makefile`; no other new dependencies.
- Handlers report failure as RESP error replies, never by throwing; a thrown exception becomes `-ERR <message>`.
- Errors visible to scripts use Valkey's error-table format: `{err="CODE msg"}`, bare messages get `ERR `.
- Spec correction found while planning: `fpconv_dtoa` is **not** already compiled in. It lives in Valkey's
  `deps/fpconv/` (`fpconv_dtoa.c`, `fpconv_dtoa.h`, `fpconv_powers.h`), not in `deps/lua/src/fpconv.c` (that is
  cjson's). Task 3 fetches it.

## Review Focus

1. **Binary-safe strings**: keys, args, `redis.call` arguments and bulk replies containing `\0` or `\r\n` must round-trip
   byte for byte. Test in Task 7 (`keysAndArgvAreBinarySafe`) and Task 2 (`bulkReplyWithCrlfIsBinarySafe`).
2. **Malformed handler reply** (empty `byte[]`, `"hello"`, truncated `"$5\r\nab"`): a script error
   `ERR unexpected reply from handler for server.call`, never a Wasm trap, and the next `eval` still works. Today's
   parser trusts the host and would read past the buffer. Test in Task 2 (`malformedReplyIsScriptError`).
3. **Large replies**: a 10,000-element array reply converts without blowing the Lua C stack (call `luaL_checkstack`
   while parsing). Test in Task 2 (`largeArrayReply`).
4. **Exception text with CR/LF** (`new RuntimeException("a\r\nb")`) must not produce a malformed RESP error; replace
   `\r`/`\n` with spaces. Test in Task 1 (`exceptionMessageWithNewlinesStaysOneError`).
5. **State leaking across evals after a failure**: a script that calls `setresp`/`set_repl` then errors must not leave
   the next eval in that state, because the reset runs at the start of every eval. Test in Task 5
   (`resetRunsEvenAfterFailedEval`).

      default byte[] setResp(int version) { /* +OK\r\n for 2, -ERR RESP3 is not supported\r\n otherwise */ }
      default byte[] setRepl(int flags) { /* +OK\r\n */ }

  call/aclCheckCmd → the command argv; setResp/setRepl → `[<int>]`; log → `[<level>, <message>]`.
- Produces (C): `static char *hostCall(int op, const char *req, size_t req_len, size_t *reply_len)` returning the
  malloc'd reply (caller frees). Later tasks call it; they never call the import directly.

### Task 5: Delegated `setresp`, `set_repl`, `log`, `acl_check_cmd`, and the per-eval reset

**Files:**
- Modify: `lua/valkey_lua.c`, `java/src/main/java/valkeylua/ValkeyLua.java` (dispatch only)
- Test: `java/src/test/java/valkeylua/ValkeyLuaTest.java`

**Interfaces:**
- Consumes: `hostCall`, `luaPushError`, `luaArgsToRequest`, the `server` table.
- Produces (C): `static int expectReply(lua_State *L, const char *reply, size_t len, const char *fn, char want)`:
  validates a non-`call` reply. `-...` → raise via `luaPushErrorBuff`; `want` (`'+'` = exactly `+OK`, `':'` = exactly
  `:0`/`:1`) mismatch → raise `ERR unexpected reply from handler for <fn>`. `fn` is `server.setresp`, `server.set_repl`,
  `server.log` or `server.acl_check_cmd`.
- Validation, verbatim from Valkey, before calling the handler:
  - setresp (`script_lua.c:1476`): `server.setresp() requires one argument.`, `RESP version must be 2 or 3.`
  - set_repl (`:1359`): `server.set_repl() requires one argument.`,
    `Invalid replication flags. Use REPL_AOF, REPL_REPLICA, REPL_ALL or REPL_NONE.`
  - log (`:1423`): `server.log() requires two arguments or more.`, `First argument must be a number (log level).`,
    `Invalid log level.`; message = arguments 2..n joined with single spaces.
  - acl_check_cmd (`:1384`): `luaArgsToRequest` errors; `:1` → `true`, `:0` → `false`.
- Per-eval reset: at the start of `eval`, before loading the script, the C side calls `hostCall(OP_SETRESP, ["2"])`
  then `hostCall(OP_SET_REPL, ["3"])`. On any error or wrong reply, `eval` returns status 1 with the error table's
  `err` text and does not run the script. (The spec says `ValkeyLua` makes these calls. Doing it in C gives the same
  behaviour and reuses one error path.)
